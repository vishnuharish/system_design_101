What is System Design?
The big picture — why systems break and how to plan them
Theory
▼
📖 Theory
System Design is the process of planning how a software application will work at a large scale — handling millions of users, storing huge amounts of data, and staying fast and reliable.

Think of it like designing a city. A small village doesn't need traffic lights or highways. But a big city needs roads, bridges, water systems, electricity grids — all working together. Software is the same. A simple app for 10 friends is easy. But building Instagram, YouTube, or WhatsApp for billions of people needs careful planning.

Key questions System Design answers:
— How do we store millions of user photos?
— How do we handle 100,000 users at the same time?
— What happens when one server crashes?
— How do we make the app fast for users in different countries?
🏫 Real-world analogy: Your school canteen works great for 200 students. But imagine feeding 200,000 students. You'd need multiple food stalls, separate queues, backup cooks, and a storage room. That's system design — planning for scale.

Client-Server Architecture
How your browser talks to the internet
TheoryJavaScriptPython
▼
📖 Theory
Every app you use has two parts: the Client (your device — phone, laptop) and the Server (a powerful computer far away that stores and processes data).

When you open YouTube: 1) Your browser (client) sends a request: "Give me the homepage". 2) YouTube's server receives it. 3) The server finds the videos and sends them back. 4) Your browser displays them. This is called the Request-Response cycle.
🍕 Pizza analogy: You (client) call a pizza shop (server) and order a pizza. The shop makes it and delivers it. You didn't bake it — you just asked for it. That's client-server!

DAY 06
Caching — Speed Up Everything
Don't compute the same thing twice
TheoryJavaScriptPython
▼
📖 Theory
Caching means saving the result of an expensive operation so you can reuse it quickly next time, instead of computing it again.

Every time someone searches "funny cat videos" on YouTube, should YouTube search all 800 million videos? No! It caches the top results. The next 1000 people get the same answer instantly from the cache.

Cache Hit = found in cache (fast ⚡). Cache Miss = not in cache, must fetch from database (slow 🐢).
🧠 Memory analogy: Your brain caches your home address. You don't look it up on Google every time — you already know it. Software caches work the same way.
💛 JavaScript Example
JavaScript — Simple In-Memory Cache
const cache = new Map();

async function getUser(id) {
  if (cache.has(id)) {
    console.log('⚡ Cache HIT — returning fast!');
    return cache.get(id);
  }
  // Slow DB call (first time only)
  console.log('🐢 Cache MISS — fetching from DB');
  const user = await fetchFromDB(id);
  cache.set(id, user);
  return user;
}
🐍 Python Example
Python — functools Cache
from functools import lru_cache

# @lru_cache saves previous results automatically!

def get_user_score(user_id):

    return user_id * 42  # Expensive computation

DAY 08
Load Balancing
Distribute traffic so no single server breaks
TheoryJavaScriptPython
▼
📖 Theory
A Load Balancer sits in front of multiple servers and distributes incoming requests so no single server gets overwhelmed. If one server dies, the load balancer routes traffic to others automatically.

Strategies:
— Round Robin: Request 1 → Server A, Request 2 → Server B, Request 3 → Server C, repeat
— Least Connections: Send to whichever server has fewest active connections
— IP Hash: Same user always goes to same server
🏦 Bank analogy: A bank has 5 counters. A manager (load balancer) directs each customer to the counter with the shortest queue. No one counter gets stuck with 100 people.
💛 JavaScript Example
JavaScript — Round Robin Load Balancer
const servers = ['Server-A', 'Server-B', 'Server-C'];
let current = 0;

function getNextServer() {
  const server = servers[current % servers.length];
  current++;
  return server;
}

// Simulate 6 incoming requests
for (let i = 1; i <= 6; i++) {
  console.log(`Request ${i} → ${getNextServer()}`);
}
// Request 1 → Server-A
// Request 2 → Server-B
// Request 3 → Server-C
// Request 4 → Server-A (repeats!)

Message Queues
Async communication between services
TheoryJavaScriptPython
▼
📖 Theory
A Message Queue lets services communicate by passing messages without waiting for each other. Service A puts a message in the queue. Service B picks it up when ready. They're decoupled — they don't need to run at the same speed.

Example: When you order food on Swiggy, your phone doesn't wait for the restaurant to confirm before showing "Order Placed." The confirmation goes through a queue and reaches you later.
📬 Mailbox analogy: You drop a letter in a mailbox. You don't wait there until the postman collects it. The postman collects it when ready and delivers it. The mailbox is the queue.
💛 JavaScript Example
JavaScript — Simple Queue Simulation
class MessageQueue {
  constructor() { this.queue = []; }

  publish(msg) {
    this.queue.push(msg);
    console.log(`📤 Published: ${msg.type}`);
  }

  consume() {
    if (this.queue.length === 0) return null;
    const msg = this.queue.shift();
    console.log(`📥 Processing: ${msg.type}`);
    return msg;
  }
}

const mq = new MessageQueue();
mq.publish({ type: 'ORDER_PLACED', orderId: 42 });
mq.publish({ type: 'SEND_EMAIL', to: 'user@mail.com' });
mq.consume(); // Processes ORDER_PLACED
mq.consume(); // Processes SEND_EMAIL

💛 JavaScript Example
JavaScript — Smart Load Balancer
class LoadBalancer {
  constructor(servers) {
    this.servers = servers.map(s => ({
      name: s, healthy: true, connections: 0
    }));
    this.index = 0;
  }

  getServer(strategy = 'round-robin') {
    const healthy = this.servers.filter(s => s.healthy);
    if (strategy === 'round-robin') {
      return healthy[this.index++ % healthy.length];
    }
    if (strategy === 'least-conn') {
      return healthy.reduce((a,b) =>
        a.connections < b.connections ? a : b);
    }
  }
}

const lb = new LoadBalancer(['A','B','C']);
console.log(lb.getServer().name); // A
console.log(lb.getServer().name); // B
console.log(lb.getServer().name); // C

DAY 15
CAP Theorem
The impossible triangle of distributed systems
Theory
▼
📖 Theory
The CAP Theorem says a distributed database can only guarantee 2 out of 3 properties at the same time:

C — Consistency: Every read gets the most recent write. All nodes see the same data at the same time.
A — Availability: Every request gets a response (even if it's not the latest data).
P — Partition Tolerance: The system works even if some servers can't communicate.

Since network failures (partitions) always happen, you really choose between CP (consistent but sometimes unavailable) or AP (always available but sometimes stale data).
📚 Classroom analogy: Teacher writes new notes on the board (Consistency). Students can always read notes (Availability). Even if some students are absent (Partition), class continues. You can't guarantee all three perfectly at once.
🔄
Consistency
Same data everywhere
✅
Availability
Always responds
🌐
Partition
Handles network splits
⚠️
Pick 2
Can't have all three
DAY 16
Database Replication
Copies everywhere for speed & reliability
TheoryPython
▼
📖 Theory
Replication means keeping copies of your database on multiple servers. If one fails, others take over. Also speeds up reads by letting users read from the nearest copy.

Master-Slave: One master handles all writes. Multiple slaves get copies and handle reads. Most read-heavy apps (news sites, social media) use this.

Multi-Master: Multiple nodes can handle writes. More complex, but highly available.
🐍 Python Example
Python — Replica Routing
import random

class DatabaseCluster:
    def __init__(self):
        self.master = "Master-DB"
        self.replicas = ["Replica-1", "Replica-2", "Replica-3"]

    def write(self, data):
        # Always write to master
        print(f"✍️  Writing to {self.master}: {data}")

    def read(self):
        # Distribute reads across replicas
        db = random.choice(self.replicas)
        print(f"📖 Reading from {db}")

cluster = DatabaseCluster()
cluster.write("new post")  # ✍️ Master
cluster.read()             # 📖 Random replica

Database Sharding
Split your database into horizontal pieces
TheoryJavaScript
▼
📖 Theory
Sharding splits a large database into smaller pieces called shards, each stored on a different server. Instead of one giant table with 1 billion users, you split them: Users 1-333M on Shard 1, Users 333M-666M on Shard 2, Users 666M-1B on Shard 3.

Sharding strategies:

— Hash-based: Apply a hash function to distribute evenly
— Geographic: Users in India → India DB, Users in US → US DB

DAY 18
Rate Limiting
Protect your API from being overwhelmed
TheoryJavaScriptPython
▼
📖 Theory
Rate Limiting controls how many requests a user can make in a time window. Prevents abuse, bot attacks, and server overload.

Example: Twitter allows 300 tweets per 3 hours. GitHub API allows 5000 requests per hour. If you exceed the limit, you get a 429 Too Many Requests error.

Algorithms: Token Bucket, Leaky Bucket, Fixed Window, Sliding Window.
💛 JavaScript Example
JavaScript — Token Bucket Rate Limiter
class RateLimiter {
  constructor(maxRequests, windowMs) {
    this.max = maxRequests;
    this.window = windowMs;
    this.requests = new Map(); // userId → [timestamps]
  }

  isAllowed(userId) {
    const now = Date.now();
    const times = this.requests.get(userId) || [];
    const recent = times.filter(t => now - t < this.window);
    if (recent.length >= this.max) return false; // ❌ Blocked
    recent.push(now);
    this.requests.set(userId, recent);
    return true; // ✅ Allowed
  }
}

const limiter = new RateLimiter(3, 1000); // 3 req/sec
console.log(limiter.isAllowed('user1')); // true
console.log(limiter.isAllowed('user1')); // true
console.log(limiter.isAllowed('user1')); // true
console.log(limiter.isAllowed('user1')); // false — BLOCKED!

Week 3 Project — Rate Limited API

Mini ProjectPython
▼
🎯 Project
Build a Flask API with JWT authentication and rate limiting. Only logged-in users can access it, and they're limited to 5 requests per minute.
🐍 Python Example
Python — Secure Rate-Limited API
from flask import Flask, request, jsonify
from collections import defaultdict
import time

app = Flask(__name__)
request_log = defaultdict(list)

def rate_limit(user, max_req=5, window=60):
    now = time.time()
    times = [t for t in request_log[user] if now-t < window]
    if len(times) >= max_req: return False
    times.append(now)
    request_log[user] = times
    return True

@app.route('/data')
def get_data():
    user = request.args.get('user', 'anonymous')
    if not rate_limit(user):
        return jsonify({'error': 'Too many requests'}), 429
    return jsonify({'data': 'Here you go!'})

Design a URL Shortener
Like bit.ly — long URLs become short ones
Full DesignJavaScript
▼
📖 Design Breakdown
Requirements: User pastes a long URL → System gives a short URL like bit.ly/abc123 → When someone visits short URL, they're redirected to original.

Components:
— API Server: Accepts and redirects URLs
— Database: Stores short→long URL mappings
— Cache: Popular short URLs cached for speed
— ID Generator: Creates unique short codes (Base62 encoding)

Estimation: 100M URLs created/day. 10B redirects/day. Need a fast DB (Redis for cache, MySQL for storage).
💛 JavaScript Example
JavaScript — URL Shortener Core
const CHARS = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';
const db = new Map(); // short → long
const cache = new Map();

function encode(num) {
  let code = '';
  while (num > 0) { code = CHARS[num % 62] + code; num = Math.floor(num/62); }
  return code.padStart(6, '0');
}

let counter = 100000;
function shorten(longUrl) {
  const shortCode = encode(counter++);
  db.set(shortCode, longUrl);
  return `https://sho.rt/${shortCode}`;
}

function redirect(code) {
  if (cache.has(code)) return cache.get(code); // ⚡ Cache hit
  const url = db.get(code);
  cache.set(code, url);
  return url;
}

console.log(shorten('https://very-long-website.com/article/123'));
// https://sho.rt/00D2h1

📖 Design Breakdown
Two approaches to building a feed:

Pull Model (Fan-out on Read): When you open Instagram, it fetches posts from everyone you follow and sorts them. Simple but slow for users who follow 1000 people.

Push Model (Fan-out on Write): When a user posts, immediately push that post to all their followers' feeds. Feeds are pre-computed and cached. Fast to read, but expensive for celebrities with millions of followers.

Hybrid (what Instagram uses): Push for regular users. Pull for celebrities. Cache all feeds in Redis for fast reads.
🐍 Python Example
Python — Feed Fan-out System
from collections import defaultdict

class FeedSystem:
    def __init__(self):
        self.followers = defaultdict(set)  # user → followers
        self.feeds = defaultdict(list)     # user → feed posts

    def follow(self, user, celebrity):
        self.followers[celebrity].add(user)

    def post(self, author, content):
        post = {'by': author, 'text': content}
        # Fan-out: push to all followers' feeds
        for follower in self.followers[author]:
            self.feeds[follower].insert(0, post)
            self.feeds[follower] = self.feeds[follower][:50]

    def get_feed(self, user):
        return self.feeds[user][:10]

feed = FeedSystem()
feed.follow('Priya', 'Virat')
feed.post('Virat', 'Just won the match! 🏏')
print(feed.get_feed('Priya'))

Design a Search Engine (Basic)
How Google finds pages in milliseconds
Full DesignPython
▼
📖 Design Breakdown
Crawling: Bots visit every webpage on the internet, follow links, and download content.

Indexing: Build an "inverted index" — a dictionary where each word points to all pages that contain it. "cricket" → [ESPN.com, BCCI.com, Cricinfo.com]

Ranking: Which page appears first? Google's PageRank algorithm scores pages based on how many other pages link to them. More links = more trusted.
🐍 Python Example
Python — Inverted Index
from collections import defaultdict

class SearchIndex:
    def __init__(self):
        self.index = defaultdict(set)  # word → {pages}

    def add_page(self, url, content):
        for word in content.lower().split():
            self.index[word].add(url)

    def search(self, query):
        words = query.lower().split()
        results = None
        for word in words:
            pages = self.index.get(word, set())
            results = pages if results is None else results & pages
        return results or set()

engine = SearchIndex()
engine.add_page('cricket.com', 'India won cricket match today')
engine.add_page('news.com', 'cricket world cup final today')
print(engine.search('cricket today'))
# {'cricket.com', 'news.com'}

Design an E-Commerce System
Handle flash sales, carts, and payments
Full DesignJavaScript
▼
📖 Design Breakdown
Services: Product Catalog, Cart, Order, Payment, Inventory, Notification

Flash Sale Problem: 100,000 people try to buy the same item at the same time. How do you ensure only one person buys the last item?

Solution: Use Redis atomic operations. Lock the inventory with a distributed lock. Only one transaction succeeds; others get "Sold Out."

Payment: Never handle money directly. Integrate with payment gateways (Razorpay, Stripe) that handle security.
💛 JavaScript Example
JavaScript — Inventory with Atomic Check
class InventoryManager {
  constructor() {
    this.stock = new Map();
    this.locks = new Set();
  }

  setStock(itemId, qty) { this.stock.set(itemId, qty); }

  async purchase(itemId, userId) {
    if (this.locks.has(itemId)) {
      return { success: false, reason: '⏳ Please retry' };
    }
    this.locks.add(itemId); // Lock it!
    const qty = this.stock.get(itemId) || 0;
    if (qty <= 0) { this.locks.delete(itemId); return { success: false, reason: '❌ Sold Out' }; }
    this.stock.set(itemId, qty - 1);
    this.locks.delete(itemId); // Unlock
    return { success: true, msg: `✅ ${userId} bought item!` };
  }
}
